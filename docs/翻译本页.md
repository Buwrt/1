# 翻译本页（app/src/main/assets/web/js/translate.js）

GitHub 网页版能靠浏览器扩展、油猴脚本翻译，但 githup 是 **WebView 承载的前端**——装不了扩展，也没有注入脚本的入口。

既然前端是你自己的，那就把翻译直接做进前端：**点一下右上角，整页英文变中文，再点一下原样还原。**

---

## 一、先看效果（不用装 App）

用浏览器打开 `demo.html`，里面是一个仿 GitHub 的英文页面（README / Issues / Releases），右上角就是翻译按钮。

它顺带是个**引擎体检工具**：打开时会挨个试翻译引擎，直接告诉你在你的网络下哪个能用。App 里走的是原生通道，能用的只会比浏览器里多。

## 二、它是怎么装进来的（已装好）

### 方式 A：一键脚本

```bash
bash install.sh ~/githup-release      # 换成你的仓库路径
```

脚本只做三件事，且可重复执行（装过会跳过）。

### 方式 B：手动三步

| 步骤 | 操作 |
| --- | --- |
| 1 | `js/translate.js` → `app/src/main/assets/web/js/` |
| 2 | `css/translate.css` → `app/src/main/assets/web/css/` |
| 3 | `index.html` 里加两行（见下） |

```html
<!-- 放在 css/app.css 那行后面 -->
<link rel="stylesheet" href="css/translate.css">

<!-- 放在 js/app.js 那行后面（顺序很重要，必须在 app.js 之后） -->
<script src="js/translate.js"></script>
```

**不需要改 `app.js`**——它会自己找到右上角按钮区挂上去，换页时自动补挂。

然后照常打包：`bash build-apk.sh`，或者 Android Studio 直接 Run。

## 三、怎么用：一个总开关

右上角的地球图标**不是「翻这一页」，是总开关**：

| 状态 | 行为 |
|---|---|
| **亮着** | 当前页翻；**换页后新页面接着翻**；进去的每个页面都会翻，直到你关掉 |
| **灭着（默认）** | 当前页还原，之后换页不再翻 |

点一下开、再点一下关。长按打开设置（换引擎、清缓存）。

翻译过程中图标会转，翻完提示"已翻译 xx 段 · 用时 · 引擎名"。

> 总开关**默认关闭**：装上不会自动翻任何页面，你亲手点开才开始。开关状态记住，重开 App 沿用。

### 换页为什么能接上

App 的路由用的是 `history.pushState()`——它**不触发 `hashchange`，也不触发 `popstate`**（后者只在后退时响）。所以只监听这两个事件的话，往前跳的每一次换页都会漏掉。

这里做了两层保险：包一层 `history.pushState/replaceState`，再用 MutationObserver 盯着 `#view`，任何换页都能跟上。

### 自动跳过这些内容

代码和标识符翻坏了比不翻更糟，所以这些一律不动：

- 代码块 `<pre>`、行内代码 `<code>`
- 文件路径（`app/src/main/java`）、仓库名（`Buwrt/githup`）
- commit sha、版本号（`v1.1.2`）、`#142` / `@someone`
- 纯数字、URL、邮箱
- **已经是中文为主的内容**（中文占比 > 35% 直接跳过，避免来回翻译）

### 翻到哪，译到哪

翻译是**滚动驱动**的：只翻屏幕上下各 600px 范围内的英文段。你往下滚，新的段落进入这个范围就立刻补翻，停下来 250 毫秒就开工。

这么改是因为原来的「首屏 + 后台翻整页」有两个毛病：

- 整页几十段一起并发，是撞上限流（有道/MyMemory）的元凶，反而更慢；
- 你滚到中间时，那段常常还没轮到，于是看到的还是英文。

现在不翻屏幕外的东西，请求量小、上屏快，滚到哪都是中文。

### 为什么以前又慢又「翻一半」，现在怎么解决的

慢和翻不完是**同一个根因**：有道 aidemo 接口有频率限制。原来每段一个请求，一屏 30 段就是 30 次请求连发——必然撞上 `411 请求频率过快`，被拒的那些段落只能兜底原文。所以你看到的就是「翻得慢、还翻一半就停」。

三处改动（都是实测出来的）：

| 改动 | 说明 |
| --- | --- |
| **换行拼批** | aidemo 对换行拼批**原样保留换行**（进几行出几行）。一屏 24 段从 24 条请求压到 3 条。实测 2.5 秒翻完 |
| **节流 800ms** | 全局排队，相邻两次请求间隔 ≥800ms，不给 411 机会 |
| **失败对半拆，绝不退逐条** | 拼批失败时退回逐条会让请求数暴涨、频率雪崩（实测十几条连发全 411）。改成把 chunk 对半拆小再试，拆到单行还失败就放弃，保持原文交给重试循环——4 秒后频率窗口早过了，自然补上 |

实测出的两个硬上限（超了报 `103` 内容异常）：**单条 ≤8 行且 ≤800 字符**。

### 卡住的段会自动重翻

网络抖一下、引擎限流，某几段没翻出来很常见。翻译完成后如果页面上还有没翻的段，**隔 4 秒自动重试一轮，最多 5 轮**——不用你手动再滑一次。翻成功的段进缓存，不会重复请求。

### 打开翻译后，页面本身加载变慢（骨架屏转个不停）

这个是**翻译把 App 的网络线程池占了**，不是翻译逻辑慢。

所有网络请求（页面自己的数据 + 翻译引擎）都走 `JsBridge` 里那一个线程池，原来只有 4 个线程。自动选引擎时会并行探测 5 家，其中 Google / DeepL 在国内根本连不上，每个都要**挂满连接超时**（原来 20 秒）才放弃——4 个线程瞬间被占满，页面自己的请求全堵在后面，于是骨架屏一直转。更要命的是探测失败没有记忆，你每换一页它就再来一遍。

三层修复：

| 层 | 文件 | 改动 | 效果 |
| --- | --- | --- | --- |
| 原生线程池 | `app/src/main/java/com/hubmobile/app/JsBridge.java` | 4 → **8** 线程 | 翻译和页面数据各走各的，不互相堵 |
| 连接超时 | `app/src/main/java/com/hubmobile/app/Http.java` | 20s → **12s** | 连不上的目标早点放手，线程不会被白占 20 秒 |
| 探测记忆 | `app/src/main/assets/web/js/translate.js` | **探测黑名单 + 2 分钟冷却** | 探测过的引擎 10 分钟内不再试；一轮全挂后 2 分钟内换页不再全量探测，直接用第一个候选硬上 |

冷却期内换页照样能翻（走的是已知引擎的正常翻译流程），只是不再做那轮"谁最快"的竞速。

## 四、翻译引擎

全部免费、开箱即用，不用注册不用 Key。默认**自动探测**：按下面的顺序并行试，谁先通就用谁，结果记下来不再重复探测。

| 引擎 | 特点 |
| --- | --- |
| **有道** | 国内直连最稳的免费引擎（aidemo 演示接口），无需 Key |
| **设备端翻译** | Chrome / WebView 系统内置，**离线、不联网、文本不出设备**。要系统装了中英语言包才可用，没有就自动跳过 |
| **DeepL** | 网页版同款接口，质量最佳；公共 IP 偶尔限流，失败段自动兜底原文 |
| **Google** | 老牌免费接口，需海外网络 |
| **MyMemory** | 兜底，全球可达，匿名有日配额 |
| ~~**微软 Edge**~~ | **已停用**：微软关闭了 Edge 翻译的公开令牌接口，`edge.microsoft.com/translate/auth` 现在直接返回 404，拿不到令牌就调不动翻译。实现保留（改 `retired: false` 即可恢复），但已移出探测链和选择列表 |

### 为什么只剩有道和 MyMemory 能用

这不是代码问题，是网络 + 厂商政策叠加的结果（2026-09 实测）：

| 引擎 | 国内手机上的实际情况 |
| --- | --- |
| 有道 | ✅ 直连可用，最稳 |
| MyMemory | ✅ 全球可达，但匿名有日配额，用完当天就不行了 |
| 设备端 | ⚠️ 看系统有没有下载中英语言包，多数国产 ROM 没有 → 不可用 |
| DeepL | ❌ 国内网络基本不可达；就算通了，公共 IP 频繁 429 |
| Google | ❌ `translate.googleapis.com` 国内不可达 |
| 微软 Edge | ❌ 官方已关闭免费接口（404） |
| 百度 | ❌ 免签接口已封（`v2transapi` 返回 errno 1022），要 token+sign |

所以**国内网络下实际上就是有道 + MyMemory 两台在跑**，这也是把它们排在最前和最后的原因。想要更稳的，就在菜单里填**自定义接口**（自建 / DeepLX / 内网都行）。

### 引擎挂了会自动换，不会把你晾在英文页上

手动选中的引擎如果整轮一段都没翻出来，模块会**记住它 5 分钟内不可用，然后自动换下一个还没试过的引擎接着翻**，全试完才认输。你只会看到一句提示：

```
「MyMemory」不可用（无配额），自动换用其他引擎…
已改用「有道」翻译
```

有两条原则：

- **手动选的引擎永远先给它机会**：用户的选择就是选择，不能因为 5 分钟前挂过就替他做主——除非那个引擎已经**停用**（微软 Edge 这种），这时才提示一次并自动改道。
- **自动探测只跳过已知挂掉的**，换页时不再每次都先撞一次 404 再降级。

两处可靠性加固（都来自实测踩坑）：

- 部分 WebView 里系统翻译的 `availability()` 会**永久挂起**，以前会把整个自动选择卡死（表现为"翻译卡在正在翻译"，换哪个引擎都没用）——现在每个探测都有超时，超时视为不可用。
- 自动选择**没有硬编码兜底引擎**：全部探测失败就返回「无可用引擎」并明确提示，不再硬塞一个必然报错的引擎——以前全挂时兜底微软，真机上就是「微软 HTTP 404」的来源。
- **原生通道的 headers 必须 `JSON.stringify`**：`JsBridge.http(id, method, url, body, headersJson)` 第 5 个参数是**字符串**，Java 侧 `new JSONObject(headersJson)`。以前直接传 JS 对象，WebView 桥接时塞不进 String 参数，headers 被**整体丢弃**——表现就是「真机上只有 MyMemory 能用，有道 / DeepL / 微软全废」（这三个都要 `Content-Type` / `Authorization`，而 MyMemory 是 GET 不带自定义头，所以独活）。同时补了浏览器 UA：`Http.java` 在没给 UA 时写 `HubMobile/1.0`，有道 / DeepL 对非浏览器 UA 不太友好。

都不通也别慌，菜单里可以填**自定义接口**（自建 / DeepLX / 内网都行）：

```
POST {"q":["文本1","文本2"], "from":"auto", "to":"zh-Hans"}
返回 {"translations":["译文1","译文2"]}  或直接返回字符串数组
```

## 五、隐私

- 请求走 `Native.http` 原生通道。桥接层**不会自动附加 GitHub Token**（token 是前端显式拼进 headers 的，见 `JsBridge.http`），所以翻译请求不携带任何凭据。
- 但**被翻译的文本本身会发给所选翻译服务商**——这是翻译的前提，绕不开。仓库私有内容介意的话，就把引擎固定到「设备端翻译」。
- 译文有本地缓存（上限 600 条），同样的内容不会重复请求。菜单里可一键清空。

## 六、实现要点

几个踩过或避开的坑，改代码时值得留意：

1. **只改文本节点的 `nodeValue`，不动 DOM 结构**——所以点击、长按、下拉刷新这些事件一个都不会被破坏，也不需要重新渲染页面。
2. **原文挂在节点上**（`node.__tr_orig`），还原时不重建页面、不重新请求接口。
3. **全局对象叫 `window.GhTranslator`，不是 `window.Translator`**——后者是新版 Chromium 自带的设备端翻译 API，占用它会在真机上跟系统打架。
4. **换页用 seq 作废进行中的请求**，避免上一页的译文迟到后写到新页面上。
5. **批量 + 缓存**：每批最多 24 段 / 3200 字符，命中的缓存不发请求；Google 那条通道用换行拼批，行数对不上时退回逐条重译，宁可慢一点也不让译文错位。
6. **headers 只能 stringify 一次**（踩过两次坑，两个方向都错）——链路是两层：

   ```
   translate.js ──▶ window.Native.http(m, u, b, headers)   ← api.js 的 JS 封装，收**对象**
                    （内部 JSON.stringify）
                    ──▶ NativeBridge.http(id, m, u, b, headersJson)  ← Java，收**字符串**
                        new JSONObject(headersJson)
   ```

   - 传**对象**给 `Native.http`：这里传对象，由 api.js 转成字符串，只转换一次，Java 侧解析正常。
   - 自己在 translate.js 里先 `JSON.stringify` 一次：Java 收到「JSON 字符串的字符串」，
     `new JSONObject` 直接抛异常 → 回调 `status 0` → **原生通道每次都失败**，只能退回 fetch 兜底。
     表现就是「只有服务端愿意给 CORS 头的引擎（有道 / MyMemory）能用，Google / DeepL 全灭」，
     而且每个请求都要先失败一次再重试，又慢又不全。
   - 反过来，直接把对象塞给 **Java 那层**（`NativeBridge.http`）也不行：WebView 桥接塞不进 `String` 参数，headers 会被整体丢弃。

   一句话：**给 `window.Native.http` 传对象，给 `NativeBridge.http` 传字符串，别多转也别少转。**

## 七、文件

本仓库里改动到的文件：

```
app/src/main/assets/web/js/translate.js               # 核心（本文全部逻辑都在这里）
app/src/main/assets/web/css/translate.css             # 按钮样式
app/src/main/java/com/hubmobile/app/JsBridge.java     # 网络线程池 4 → 8（不让翻译堵住页面请求）
app/src/main/java/com/hubmobile/app/Http.java         # 连接超时 20s → 12s（连不上就早点放手）
app/src/main/AndroidManifest.xml                      # 平板 / 大屏适配（可调整尺寸 + 方向不锁死）
app/src/main/assets/web/css/app.css                   # 平板断点：内容限宽居中
```

想在浏览器里先预览 / 给引擎做体检，用 `demo.html`（单独提供的那份，不在仓库里），
或者直接在手机上长按翻译图标看提示。

调试时可以在控制台用：

```js
GhTranslator.probe()      // 探测所有引擎，返回各自是否可用
GhTranslator.translate()  // 翻译当前页
GhTranslator.restore()    // 还原
```
